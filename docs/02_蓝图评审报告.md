## 二、发现清单

### 重要（5 条）

**F1【重要】前置归因只有数据结构，无逻辑落点**
- 位置：ARCHITECTURE §1/§3（domain/alu.ts）、CONTRACTS §1（Alu.prereq）、TRACEABILITY §4.6 行
- 事实源依据：PRD §4.6②"**前置归因**：一张卡答错时，沿**依赖图向上游追溯**检查前置 ALU——很多'错'是前置没懂。这是通用机制。"——这是 PRD 点名的自研三件套之二。
- 问题：蓝图仅给了 `Alu.prereq` 数据结构，"答错→沿图向上游追溯"的模块/函数落点缺失；CONTRACTS 无归因结果字段或 API；TRACEABILITY §4.6 行落点仅写"domain/alu.ts（prereq 图）"，属"仅表面出现"。对照：同节"节奏编织"有 `pickReviewBatch`、"首页欠账排序"有 R 升序，均有函数落点，唯前置归因没有。
- 修复建议：在 domain（建议 `queue.ts` 或 `decision.ts`）增加归因函数落点，并在 CONTRACTS 增加归因结果表达（如 `AnswerRecord` 或 `judge` 事件增加 `prereqSuspect?: AluId[]` 字段）；TRACEABILITY §4.6 行补该落点。

**F2【重要】队列来源②"用户主动收藏/标记"无落点，矩阵却声称覆盖**
- 位置：CONTRACTS §1/§2（Alu/AluUserState/QueueItem 无收藏字段）、TRACEABILITY §4.6 行（"队列三来源"）
- 事实源依据：PRD §4.6③"**队列来源汇总**：①标准/高质量档讲完生成的卡 ②**用户主动收藏/标记** ③搜索/识图摄入后转成 ALU 的内容"。
- 问题：TRACEABILITY §4.6 行条款要点写"队列三来源"并声称全覆盖，但来源①有 `card_generated` 事件、来源③有 pipeline/tools 落点，来源②在契约中无字段、无入口组件（`isPriority` 是高质量档自动升级，语义不同）。矩阵在此处是"表面覆盖"。
- 修复建议：或补契约字段（如 `AluUserState.userFlagged: boolean`）并指定入口；或若产品入口形态未定，按既有 D4 模式列入待裁决。

**F3【重要】UID §5.4"模糊不记账"与 PRD"答错/模糊→间隔↓"两事实源矛盾，蓝图静默取 PRD 口径、未列裁决**
- 位置：CONTRACTS §2（`gradeToRating: fuzzy→Hard(2)`）、ARCHITECTURE §4（硬规则 3 "review 档 wrong/fuzzy 判定→自动注入 remediation"）
- 事实源依据：PRD §4.5 状态机图"**答错/模糊 → 间隔↓ 并回落到标准档补讲**"、§4.6①"答错/模糊→间隔↓"；UID §5.4"'模糊'不是废票，是脚手架的入口——选它就走'再讲一遍'，**不记账**"。三处事实源两派口径。
- 问题：蓝图落法（fuzzy→Hard 进 FSRS + fuzzy 触发补讲）与 PRD 状态机图一致、与 UID"模糊走再讲一遍"也一致，唯独与 UID"不记账"三字冲突。蓝图未在待裁决清单或正文标注该矛盾——M2 实现者读 UID 会得出相反实现。
- 修复建议：列入待裁决（建议 D8），向用户确认"模糊"是否写入 FSRS（蓝图当前=写入并降间隔）。确认前默认按 PRD 口径（产品事实源优先级更高），但必须在 CONTRACTS §2 注释中显式标注"UID §5.4'不记账'与本映射冲突，按 PRD §4.6 落"。

**F4【重要】PRD §3 复习"一轮 3~6 分钟"与 §10.3 复习"60~90s/轮"矛盾，蓝图按 §10.3 取值未标注**
- 位置：CONTRACTS §9（`FlowParams.sessionMinutes`，注释引用 §10.3）
- 事实源依据：PRD §3 档2"一项多久：10~30 秒/卡；**一轮 3~6 分钟**"；PRD §10.3 表复习行"单次时长 **60~90s/轮**"；而 60~90s 恰为 §3 档1 快速回顾的时长（"快速回顾：单次 60~90 秒"），§10.3 复习行疑似误植。UID §10.3 系复制 PRD，同病。
- 问题：蓝图取 §10.3 的 60~90s，未识别也未标注两节矛盾。该值直接进入提示词时长预算与"有界会话"话术（§10.1①"再 3 张清完今天"），影响复习档产品形态。
- 修复建议：列入待裁决（建议 D9）：复习轮时长取 3~6 分钟（按 §3）还是 60~90s（按 §10.3）。裁决前在 FlowParams 注释并列标注两个出处。

**F5【重要】今日决策优先级"补讲 > 复习 > 新学"是蓝图补位决策，未标注来源**
- 位置：ARCHITECTURE §4（TodayDecision 优先级）、CONTRACTS §3 注释
- 事实源依据：PRD §5.6 表仅写"首页'今天该学的一件事'：复习欠账（R 值）vs 新内容 vs 补讲"，**未定义三者顺序**。PRD §2 以"欠账牵引"为四牵引力之首。
- 问题：蓝图将"当日补讲 > 到期复习 > 新学建议"写为定序，方向合理（补讲是复习失败的即时后续）但属方案留白处的补位。对照同类留白"已稳固阈值"（PRD §4.2 同样未给值）蓝图走了待裁决 D5——本条应同等处理，否则用户到验收才发现首页行为与预期不符。
- 修复建议：列入待裁决（建议 D10）或至少在 ARCHITECTURE §4 标注"PRD 未定序，此为蓝图补位，请确认"。

### 建议（12 条）

**F6【建议】TodayPlan.suggestion 类型过宽**：CONTRACTS §3 `TodayPlan.suggestion: TodayDecision` 含 `{kind:'first_run'}`，而回访首屏（UID §2.2）不会出现 first_run。建议改为 `Exclude<TodayDecision, { kind: 'first_run' }>`。

**F7【建议】补讲子会话的事件表达不完整**：CONTRACTS §7 `TaskInstruction.mode: SkillName | 'remediation'` 允许 remediation，但 §9 `SessionEvent.session_start.skill: SkillName` 不含；`remediation_start/done` 事件已有，但"补讲子会话是否发 session_start"未规定。建议注释明确：补讲子会话仅发 `remediation_start`/`remediation_done`，不发 `session_start`。

**F8【建议】ARCHITECTURE §13 M7 验收项不全**：写"红橙帧<3%、P95<16.7ms、0.5s 首屏、中低端机实测"，缺 UID §7.3 的"冷启动中端机≤1.5s"与"帧间隔方差单列"（后者 UID 特别强调"不看平均值"）。TRACEABILITY §7.3 行已兜住，建议 §13 对齐补全，避免 M7 执行者只看里程碑表漏项。

**F9【建议】难度刻度换算规则未定**：CONTRACTS §1 `Alu.difficulty` 注释"难度 1~5（附录样例 0~3，统一为整数刻度，0=资源型占位）"——已标注差异但未给换算规则。PRD 附录样例 difficulty∈{0,1,2,3}，若 M5 种子包照抄，3 在旧刻度为最高、新刻度仅为中等。建议给出映射（如旧 3→新 4~5）写入契约注释。

**F10【建议】"进度细线"落点混写**：UID §三"每还一张，屏幕右下角那一条**细线**缩短一格……不做成横贯全屏的粗条"。TRACEABILITY §三行将其落点写为 `components/ProgressRing+SessionEndCard`——ProgressRing 是掌握度进度环（UID §四："高质量/成长：掌握度"），与还款进度细线是两个语义。16 零件中确无细线零件（此为 UID 自身留白，非蓝图原创问题），但矩阵把两回事混为一谈会误导 M3。建议：为进度细线指定落点（Session 页内局部组件即可，不必进 catalog），并修正 TRACEABILITY §三行落点。

**F11【建议】回链校验从"复用现成实现"变为"自实现"**：PRD §4.3"**回链不自研**……直接复用现成的 citation / span-anchor 实现"；ARCHITECTURE §9 改为"用现成 citation/span-anchor **思路**的字符串区间命中实现"。npm 生态确无可直接用的 citation/span-anchor 包，蓝图务实处理可以理解，但与 PRD 字面相悖。建议在 §9 注明"现成可直接依赖的实现不存在，故按该思路以最小代码实现"，留痕差异。

**F12【建议】SkillParams.goal 枚举越界扩展**：PRD §3 档1 仅定义两态"目标=建立地图 vs 目标=唤醒"（即 map/recall）；CONTRACTS §6 `goal: 'map' | 'recall' | 'understand' | 'master'` 中后两个无 PRD 显式出处。建议标注为蓝图扩展，或收敛到 map/recall。

**F13【建议】技能包"数据结构"要素无对应字段**：PRD §7.2 技能包四要素"指令/提示词模板 + 所需工具声明 + **数据结构** + 组件按名引用列表"；SkillManifest 有 promptTemplate/tools/components，无数据结构要素。若意图为"本档使用的 ALU/消息结构由契约全局承担"，建议在 CONTRACTS §6 注明一句，避免 M2 实现者按 PRD 字面找字段。

**F14【建议】storage/repos 清单与 Collections 不齐**：ARCHITECTURE §1 写 repos "alu/state/review-log/profile/session/settings/gate"（7 个），CONTRACTS §10 Collections 有 9 个集合（多 `grayscale`、`budget`）。建议对齐目录注释。

**F15【建议】压缩边界表述歧义**：ARCHITECTURE §5 "只动**第④段之后**，绝不改缓存前缀"——含不含第④段（Skill 模板）两解。不动④其实更利于会话内缓存命中（与 PRD §7.6"换档才会让④失效"一致），但表述应消歧，建议改为"只压缩④~⑧，①②③前缀绝不改写"（或明确含/不含④）。

**F16【建议】深度档成功率单值化未注明**：CONTRACTS §9 `targetSuccessRate` 注释"深度0.75"是 PRD §10.3"70~80%"的取中单值（程序化判定需单值，合理），建议注明"取区间中点，可配置"。

**F17【建议】TRACEABILITY 个别行"要点有列、落点缺"**：§5.6 行要点列"保持率与催收"（PRD：临近目标期限调高保持率、压缩新内容）但落点无对应——机制上 `createScheduler(requestRetention)` 已参数化，"何时调"（活跃时段+目标期限）的规则落点缺；§10.2 行要点列"过程型话术"与"比上次错得少"，落点未对应（前者应入提示词②段/技能包，后者可由 review_log 派生，建议注明派生落点）。另 §7.8 行未列 PRD"A/B 调整 description 措辞"（运营手段，可不落代码，但矩阵行应显式标注"不落代码/运营项"以免 M7 追溯时当缺失）。

**F18【建议】两处笔误**：CONTRACTS §5 "注册表**条手**"（应为"条目"）；§2 "画像**节奏画像**可调"（应为"学习节奏画像"）。
